Manuel d'utilisation
Installer, décrire un réseau, lancer une simulation, lire le résultat
Les commandes et les champs décrits ici sont lus dans le logiciel au moment de la génération, et non recopiés d'une note : une option qui change, et ce manuel change avec elle.
Version du moteur : 0.1.0 — généré le 12/11/2026 (UTC)
1. Ce que fait ce logiciel
lsim simule un réseau LoRaWAN : des capteurs qui émettent, des passerelles qui écoutent, un serveur qui commande le débit, et un canal radio qui perd ou laisse passer les trames. Il répond à des questions qu'on pose avant de déployer : combien de trames arrivent, à quelle distance, avec quelle autonomie, et à quelle vitesse le réseau réagit à une commande.
Le résultat n'est pas une estimation : c'est un calcul déterministe. Deux exécutions de la même graine donnent les mêmes compteurs, octet pour octet. C'est ce qui permet de comparer deux réglages — si le hasard s'en mêlait, une différence entre deux runs ne voudrait rien dire.
1.1 Les quatre manières de s'en servir
Mode | Pour quoi | Où commencer
Ligne de commande | Lancer un scénario écrit à la main, produire un Parquet, un rapport ou une carte | §3
Bibliothèque Python | Enchaîner des variantes, balayer un paramètre | §4
Atelier 3D (studio web) | Poser un réseau à la souris, le régler, observer le run, faire les exercices | §6
Serveur d'intégration | Raccorder de vraies passerelles (Semtech UDP ou Basic Station) et des jointures réelles | §7
1.2 Les trois idées à connaître avant de commencer
Le scénario est validé strictement. Un champ inconnu est refusé, au lieu d'être ignoré : une faute de frappe dans un nom de champ est signalée, elle ne devient pas un réglage absent.
Rien n'est émis tant que rien n'est réglé. Un scénario sans environnement, sans région et sans profil d'énergie reste exactement celui d'avant : ses chiffres et son empreinte ne bougent pas. Ajouter une option ne change jamais rétrospectivement un résultat déjà obtenu.
Une grandeur non mesurée n'est pas publiée à zéro. Un run qui n'a pas mesuré l'énergie n'a pas de colonne d'énergie ; un run sans descente n'a pas d'attente. Une case vide se lit « pas de mesure », un zéro se lirait « mesure nulle » — et les deux ne veulent pas dire la même chose.
2. Installation
Prérequis : Python ≥ 3.10, CMake, et un compilateur C++17. mbedTLS est récupéré automatiquement par CMake — un accès à GitHub est donc nécessaire à la première configuration.
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
pip install -e "python[data,report,test]"
La bibliothèque native est cherchée dans build/. Si elle est ailleurs — paquet binaire, autre répertoire de construction — on l'indique par une variable d'environnement :
export LSIM_LIBRARY=/chemin/vers/liblsim_core.so
Un paquet binaire du cœur natif (Linux) se construit avec scripts/package_native.sh : il produit une archive et son empreinte SHA-256 dans dist/. Les paquets macOS et Windows ne sont pas construits dans cet environnement.
2.1 Vérifier l'installation
La commande suivante lance un scénario d'exemple et écrit un Parquet. Si elle aboutit, le cœur natif est trouvé et le scénario est valide.
python -m lsim run examples/quartier_sf9.yaml -o resultats.parquet

4. Utilisation en Python
La bibliothèque sert à ce qu'une ligne de commande ne sait pas faire : balayer un paramètre, comparer deux variantes, enchaîner des runs dans une seule session.
from lsim.export import run_scenario
from lsim.scenario import load_scenario

scenario = load_scenario("examples/quartier_sf9.yaml")
result = run_scenario(scenario, energy_profile="rak4631")
print(result.pdr, result.totals.received)
print(result.rows[0].energy_per_message_j)
Le hash du scénario est stable : deux exécutions avec la même graine donnent les mêmes compteurs. C'est cette propriété qui rend légitime la comparaison de deux variantes — et c'est pour elle que l'empreinte du scénario est écrite dans les métadonnées du Parquet.
4.1 Ce qu'on peut interroger directement
Chaque grandeur du modèle est exposée par une fonction, sans passer par une simulation. C'est ainsi qu'on vérifie une valeur avant de la croire :
from lsim import radio
from lsim.lora import RadioConfig, time_on_air_ns

radio.receiver_sensitivity_dbm(9, 125_000) # sensibilité SF9 / 125 kHz
radio.free_space_path_loss_db(1000, 868.1e6) # perte en espace libre
time_on_air_ns(RadioConfig(spreading_factor=9), 10) # temps d'antenne (ns)

5.5 Le profil d'énergie
Deux matériels sont modélisés. Le profil se choisit par le scénario (energy.profile), par l'option --energy-profile, ou par défaut ; l'ordre de priorité est : option de ligne de commande, puis YAML, puis défaut.
Profil | Matériel | Rx 125 kHz | Veille
rak4631 | RAK4631 (nRF52840 + SX1262, module) | 17.0 mA | 2.00 µA
sx1262-stm32l072 | SX1262 (datasheet) + STM32L072 (MCU) | 4.6 mA | 1.03 µA
Profil par défaut : rak4631. Les réserves attachées à ces valeurs — notamment le Rx du SX1262 non publié au-delà de 125 kHz — sont dans le manuel technique §4.2.
5.6 Ce que le YAML ne porte pas
Aucun frontal RF : ni rf: à la racine, ni rf: dans un groupe — le champ est refusé. Les gains d'antenne et les pertes de câble se déclarent uniquement dans l'API Python, par DeviceRf et GatewayRf. Un scénario chargé depuis YAML décrit donc une population sans frontal ; pour mesurer un gain d'antenne, il faut passer par l'API. Ce n'est pas une restriction oubliée : c'est ce qui garantit qu'un scénario écrit avant l'introduction des frontaux garde exactement ses chiffres.
6. L'atelier 3D (studio)
L'atelier est l'interface graphique : on y pose un réseau à la souris, on le règle, on lance un run, et on lit ce qui s'est passé. Il se lance en deux processus — l'API, puis le studio qui s'y adresse par un proxy.
python -m lsim.api_server issue-token --tokens tokens.json --owner alice
python -m lsim.api_server serve --tokens tokens.json --runs-db runs.sqlite --port 8765
cd web && npm ci && LSIM_API_URL=http://127.0.0.1:8765 npx vite --port 5173
Le studio est alors servi sur /studio.html. Le jeton est saisi dans la page ; il reste dans l'onglet et n'apparaît jamais dans une URL. Pour une instance locale sans saisie, l'option --auto-token <propriétaire> fait émettre un jeton au démarrage — à n'employer que sur une machine de développement, puisqu'elle désactive l'authentification.
6.1 Le tour de l'interface
Zone | Ce qu'on y fait
Barre d'outils | Nouvelle session, suppression, annuler et rétablir, enregistrer et ouvrir un chantier
Palette | Glisser un équipement sur la carte 3D pour le poser : passerelle, relais, capteur, serveur
Vues | Carte 3D (CesiumJS) et plan 2D métrique — les deux tracent les liaisons observées
Panneau d'observation | Simulation, Journal, Trame, Runs, Exercice, Obstacles
Fenêtres d'équipement | Une par équipement, trois onglets : Physique, Config, CLI. Déplaçables, pour comparer deux configurations côte à côte
6.2 L'onglet Runs : revoir et comparer
Un chantier garde ses seize derniers runs. L'onglet les liste du plus récent au plus ancien, avec la graine, la date, l'état et les grands nombres. Deux boutons par ligne :
Revoir rouvre un run : ses chiffres, son plan et son journal remplacent ceux de l'écran. Le chantier ne bouge pas.
Comparer met le run choisi face au run affiché, avec l'écart. Seules les grandeurs mesurées par les deux runs sont comparées : un écart calculé contre une case vide inventerait une différence.
Un run non terminé ne publie aucun chiffre : ses colonnes restent vides plutôt qu'à zéro. Un run sorti des seize n'est pas effacé, il cesse d'être rattaché — il reste consultable par son identifiant.
6.3 Le serveur de réseau
Le serveur ne se configure pas : c'est lui qui commande le débit, les canaux et les descentes. Sa fenêtre montre donc ce qu'il a **vu** du run, par équipement : trames remises sur émises, pertes hors portée puis en collision, débit commandé, canaux laissés au terminal, et les commandes envoyées quand le run en a planifié.
Rien n'y est recopié depuis les formulaires : un champ que le run n'a pas observé reste vide, et la flèche SF7 → SF9 n'apparaît que si le serveur a commandé un changement **et** que le terminal l'a appliqué. Sinon elle recopierait le réglage de départ en laissant croire à une décision du réseau.
6.4 Obstacles, shadowing et hauteurs
Un mur se trace au rectangle sur le plan métrique. Chaque mur porte une atténuation saisie en dB, ou un matériau et une épaisseur dont le moteur calcule la perte (UIT-R P.2040-4). Rien n'est émis tant que rien n'est réglé.
Réglage | Ordre de grandeur mesuré
Mur en travers, 6 dB | à 10 km SF10 : 20 reçues sur 20 → 0 sur 20
Hauteur de passerelle | face à un mur de 12 m : 0 à 15 m, 20 sur 20 à 40 m
Shadowing σ = 8 dB | à 10 km, 40 graines : 30 restent entendues
Matériau à 868 MHz | 12 des 15 hors plage documentée : perte extrapolée
Le caractère extrapolé est affiché à côté du matériau, et l'atténuation saisie reste le chemin par défaut.
6.5 Annuler et rétablir
L'historique vit côté serveur, parce que le CLI y vit aussi : annuler « region US915 » restaure la configuration de l'équipement, pas seulement la case que l'interface affichait. Un geste par opération — ajout, retrait, déplacement, ligne CLI qui change la configuration, réglages de capteur, modèle de passerelle, relief, environnement, ADR, protocole. La navigation n'en est pas un, ni un geste sans effet : quatre lignes tapées pour régler une région s'annulent d'un seul coup, et déplacer un équipement sur place n'empile rien.
Les deux boutons sont grisés **avec leur raison**, et nomment l'opération qu'ils vont annuler. Profondeur 50. Les piles ne sont pas écrites dans le fichier de runs : une session rechargée après redémarrage repart sans historique.
7. Les exercices notés
L'atelier propose des exercices corrigés automatiquement. Les critères et la solution restent côté serveur : le navigateur n'envoie jamais de résultat, il soumet l'identifiant d'une session, et le serveur la note sur l'état qu'il détient. Tricher consisterait à modifier le serveur, pas la page.
Chaque exercice a deux indices, révélés un à un ; chaque indice retire deux points, avec un plancher à zéro. Le catalogue ci-dessous est lu dans le serveur.
Exercice | Titre | Points | Indices
eu868-passerelle | Configurer une passerelle frontière sur EU868 | 20 | 2
relais-deux-sauts | Ajouter un relais à deux sauts au plus | 30 | 2
us915-sous-bande | Choisir la sous-bande US915 et vérifier la réception | 30 | 2
latence-frontiere | Mesurer la latence de remise au LNS | 20 | 2
au915-sous-bande | Configurer AU915 sur la sous-bande 5 | 30 | 2
as923-sans-sous-bande | Configurer AS923 et son serveur réseau | 30 | 2
relais-bande-large | Réduire la durée d'émission du mesh | 30 | 2
join-flotte-etalee | Une flotte qui joint au même instant n'émet rien | 40 | 2
adr-debit-observe | Faire changer le débit par le serveur, et le prouver | 40 | 2
9 exercices, 270 points au total.
7.1 Ce que les exercices exigent, et pourquoi
Le plus exigeant n'est pas le plus long : c'est celui qui demande de prouver, et non de cocher. Dans « Faire changer le débit par le serveur, et le prouver », la case ADR cochée rapporte dix points ; les vingt autres ne tombent que si le run a **observé** un SF final plus bas que le SF de départ. À vingt messages la commande part mais le terminal ne l'applique pas encore : il en faut quarante, et c'est l'élève qui doit le découvrir en lisant le run.
De la même manière, « Une flotte qui joint au même instant n'émet rien » se corrige en étalant les départs : quatre capteurs qui émettent leur join-request à la même seconde sur le même canal se collisionnent, et personne n'est accepté. Le run passe alors de zéro à vingt uplinks de données — la leçon est dans le chiffre, pas dans l'énoncé.
7.2 Où se terminer
Un exercice se termine dans l'atelier, pas seulement au clavier : les réglages qu'il demande sont atteignables par les fenêtres de configuration, et non par la seule console. C'est une propriété vérifiée par les tests, exercice par exercice — un exercice qui obligerait à ouvrir la console serait un exercice qui enseigne un outil au lieu d'enseigner un réseau.
8. Raccorder de vraies passerelles
Le simulateur sait aussi se comporter en serveur d'intégration : une passerelle réelle peut y envoyer ses trames, et le serveur de jointure répond. Deux protocoles sont servis.
Protocole | Transport | État
Semtech UDP (GWMP v2) | UDP | PUSH_ACK, routes PULL_DATA, join-accept en PULL_RESP à tmst + 5 s
Basic Station | WebSocket | router-info, router_config, jreq, updf, dnmsg, dntxed, timesync
Le détail des formats, des bornes et des vecteurs officiels vérifiés est dans docs/USAGE.md §5bis et §5ter.
Le registre de jointure garde DevNonce et RJcount par dispositif, n'écrit qu'après vérification du MIC, et se persiste dans une base SQLite protégée par MIC. Un registre absent ou non rechargé remet les compteurs à zéro : c'est une fenêtre de rejeu. Le serveur doit donc recharger sa sauvegarde avant de servir des jointures — la remarque vaut pour une mise en production, pas pour un essai.
LR-FHSS n'est pas géré : les uplinks DR5/DR6 de US915 et la modulation LRFHSS sont refusés explicitement, et un test le vérifie. Mieux vaut un refus clair qu'un silence qui laisserait croire à une modulation simulée.
9. Lire un résultat sans se tromper
La plupart des erreurs d'interprétation viennent de quatre confusions. Elles sont faciles à éviter, à condition de savoir qu'elles existent.
On croit lire | En réalité
« Le PDR est de 0 % » | Le run n'a peut-être mesuré aucune trame. Une colonne vide n'est pas un zéro ; le simulateur ne publie pas de zéro là où il n'y a pas eu de mesure
« L'ADR a changé le débit » | La case dit ce qui a été demandé. Le SF final, dans les résultats du run, dit ce qui a été appliqué — et il peut être absent sans que rien n'ait échoué
« La passerelle entend à 40 km » | La bascule est le point où le bilan de liaison change de signe, pas une portée garantie : il n'y a ni fading ni probabilité
« Ce matériau atténue de 8 dB » | À 868 MHz, 12 des 15 matériaux sortent de la plage documentée : la perte est extrapolée, et l'interface le dit
9.1 Les indicateurs et ce qu'ils comptent
Indicateur | Ce qu'il compte | Ce qu'il ne compte pas
PDR | Trames reçues sur trames émises | Les trames jamais émises faute de canal disponible
Latence | Le temps d'antenne | Ni file d'attente, ni backhaul : c'est un plancher, pas une estimation de bout en bout
Occupation | Le temps où la passerelle est occupée | Les interférences venant d'un réseau tiers
Courant moyen | Le courant d'un message par période, en classe A | La capacité de la pile, et donc l'autonomie en années
9.2 Quand le résultat surprend
Trois causes reviennent, dans cet ordre. Un canal hors du plan régional : le scénario est refusé au chargement, le message le dit. Un duty cycle trop restrictif pour la période demandée : les messages s'espacent d'eux-mêmes, et le nombre de trames émises baisse sans que rien n'échoue. Une distance de référence d₀ qui n'est pas celle qu'on croyait : à n = 2 elle n'a aucun effet, à n = 2,7 elle décale tout de 7 dB par décade.
Pour trancher, le plus court est de mesurer la grandeur directement plutôt que de raisonner sur le scénario : radio.receiver_sensitivity_dbm, free_space_path_loss_db et time_on_air_ns répondent en une ligne, et ce sont les mêmes fonctions que le simulateur appelle.
